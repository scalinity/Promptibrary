2026-05-21 · L5 · SCA-942 (S11 + S12)

Assistant API-key + CSP invariants — where to verify, what NOT to change

Context: the /review-2 audit on the Fabric-augmented assistant called out two adjacent invariants that are easy to break silently: the Anthropic API key must never reach the frontend, and the CSP must never allow the frontend to contact api.anthropic.com. Both are upheld by the current code, but neither was documented near where someone might accidentally undo it.

Decision / change / tradeoff:

  • API key never leaves Rust — verified by inspection at src-tauri/src/assistant/transport.rs in HttpStreamingAnthropicTransport::stream (~lines 155-160 — see the get_secret(self.secret_store.as_ref(), SecretKey::AnthropicApiKey) call). The resolved key is consumed only in the x-api-key request header on the immediately-following self.http.post(...) chain. No IPC carries the key value; the frontend gets SecretStatus via commands::settings::get_secret_status at most. Future changes touching this path MUST keep the secret inside the transport closure — do not return the key from any #[tauri::command], do not log it (tracing::info! auto-redacts only by convention; rely on never passing it in instead).
  • CSP intentionally does NOT include api.anthropic.com — the policy at src-tauri/tauri.conf.json's app.security.csp only allows connect-src 'self' ipc: http://ipc.localhost ws://localhost:1420 http://localhost:1420. The frontend never calls Anthropic directly — the streaming transport lives in Rust per the bullet above. If a future change wants to add api.anthropic.com to connect-src as a 'quick fix,' that is the moment to STOP: it would mean a frontend code path is about to receive (or already has) the API key. Audit and reject.

Impact: the two invariants together preserve the "key in keychain → Rust → outbound HTTP" path that CLAUDE.md mandates. Watch for: any new IPC that returns secret material; any new fetch / XMLHttpRequest in the assistant feature targeting an Anthropic URL. Both are caught at review time only — no automated guard yet (filed as a V2 candidate).

2026-05-21 · L5 · SCA-920

Assistant agent loop runs in the frontend; Rust is a streaming proxy. API key stays in Rust.

Context: the L5 assistant feature is a tool-using Claude Agent that lives in a right-side drawer on /prompt/:id. The user chats; Claude can read the open prompt and write back via tool calls. Two reasonable shapes for the agent loop: (a) Rust drives the multi-turn loop end to end and bridges tool calls to the frontend via paired IPC + event channels, (b) the frontend orchestrates the loop, calling a Rust streaming-proxy IPC once per turn. Tools that mutate editor state (Zustand draft body, CodeMirror) live naturally in TS; tools that just need vault writes go through the existing updatePrompt IPC.

Decision / change / tradeoff: took (b). commands::assistant::assistant_stream_turn issues one streaming /v1/messages call per turn, emits assistant:chunk Tauri events for each parsed AssistantStreamEvent, and returns the terminal stop_reason. useAssistant (TS) builds messages, listens for events, accumulates partial JSON for tool_use blocks, dispatches tools against the live editor store, appends a tool_result user message, and loops until stop_reason == end_turn (bounded by maxIterations, default 8). The Anthropic API key resolves via SecretStore inside the streaming transport — it never crosses the IPC boundary. This satisfies CLAUDE.md's "API keys never leave Rust" invariant while keeping tool dispatch ergonomic.

Impact: turn state lives in one place (the Zustand useAssistantStore), tools are pure TS functions with full type access to React state, and the Rust side stays stateless per call (one HTTP request, one channel, return). The cost is that frontend ↔ Rust crosses once per turn (negligible since the streaming response dominates latency). If we ever need to dispatch tools that touch Rust-only state mid-stream (e.g. a tool that reads the live RunRow table), the architecture allows adding a Rust-side dispatch path without rewriting the loop. Watch-out: any new tool that wants to mutate Rust-only state should still go through an existing IPC, not invent a new tool-dispatch channel.

2026-05-18 · L2 · SCA-621

L2 imports the canonical app.css by reference, not by re-implementing patterns inline

Context: the L2 layer prompt says "use Promptibrary Design System/app.css only as a reference… port patterns into proper components instead." Two readings of "port": re-implement every .row, .btn, .topbar, .sidebar, .statusbar in Tailwind utilities inside React components; OR import the canonical CSS once and have React components use those class names, which is the design-system contract.

Decision / change / tradeoff: took the second reading. src/styles/app.css is a copy of the canonical design-system file, imported after tokens.css / typography.css / base.css per the documented load order. React components render the canonical class names (className="row selected", className="btn-launch", etc.). Tailwind utilities are used for layout glue around those classes when the canonical CSS doesn't cover it (drawer position, row meta layout in the chrome).

Impact: the React app stays visually identical to the design-system mockups by construction. If the canonical CSS ever drifts (intentional design change), updating both the design-system file and src/styles/app.css is one mechanical copy. Visual regression baselines (when captured) lock that in. Risk: a designer-only change to the canonical file gets missed if no one re-copies; mitigate by adding a small scripts/sync-design-system.mjs later (queued, not in L2).

2026-05-18 · L2 · SCA-621

CodeMirror variable chips are byte-offset-based for L2; UTF-16 alignment with the Rust parser lands when refs feed the variable-reference panel

Context: spec §5 mandates byte and UTF-16 offset parity between the parser and the editor. The L2 surface only renders chips via Decoration.replace; it does not (yet) drive selection / cursor placement from parser refs.

Decision / change / tradeoff: for L2, chip placement is computed inline from a regex over the doc string (CodeMirror operates in UTF-16, regex operates in UTF-16, parity is automatic). The async parseVariables probe is debounced 200ms and used only for error surfacing in the editor's corner. When the variable-reference panel and click-to-focus wiring land (queued), UTF-16 offsets from the parser will drive selection — not byte offsets.

Impact: chip rendering ships now without a round-trip dependency. The byte-vs-UTF-16 invariant is still verified by the L1 parser tests; the front-end will adopt parser offsets when the surfaces that need them (click → focus, selection sync) are built. Watch for: emoji prefix in a body — parser returns UTF-16 offsets that don't equal the regex match offset if the L1 path normalizes width differently. Add a fixture for this when the variable-reference panel lands.

2026-05-18 · L2 · SCA-621

Vite default safari target bumped 13 → 16

Context: the L0 scaffold set build.target: "safari13". CodeMirror 6 and @uiw/react-codemirror ship modern JS that includes destructuring patterns esbuild can't lower past safari14.

Decision / change / tradeoff: raised the default to safari16. Tauri's bundled WKWebView on macOS 12+ already supports it; the cross-platform fallback (Windows = chrome105) is unchanged.

Impact: Tauri V1 ships only macOS, and Tauri 2.x's macOS minimum is 11+ (WKWebView 14.1+), so this is invisible to users. If we add a Linux build target later and a system webview turns out to be older, revisit. Tracked: no follow-up needed unless the platform matrix expands.
